# Release

Four repos, one build. All are checked out next to this one.

- **this repo** — source. The archive is built from this tree. Tag the shipped commit here.
- **Stillmake/releases** (`../releases`) — binaries and release history for every Stillmake app. GitHub Releases hold the notarized DMG. `__SLUG__/changelog.json` is the full release history, the only file edited by hand. `__SLUG__/version.json` is the in-app update feed: the newest six entries, generated by `scripts/feed.mjs` and never edited by hand.
- **Homepage repo** (optional) — the site. Each build reads `__SLUG__/changelog.json` and `__SLUG__/version.json` from Stillmake/releases (a sibling checkout locally, a second checkout in CI); no release commits land here.
- **Stillmake/homebrew-tap** (`../homebrew-tap`) — `stillmake/tap/__SLUG__`.

## Versioning

Version and build are whatever the DMG carries — read them from the archive, never invent them. `changelog.json` and the GitHub release copy them.

- Source tag: `{marketing}`, e.g. `1.0`.
- Stillmake/releases tag: `__SLUG__-{marketing}-{build}`, e.g. `__SLUG__-1.0-155`.

## Flow

### 0. Check `gh` is signed in

Before anything else, verify `gh` is authenticated. Step 4 depends on it.

```bash
gh auth status
```

If this reports not logged in (or fails for any reason), **stop here** and remind the user to run `gh auth login` before continuing. Do not proceed to step 1 until it succeeds.

### 1. Confirm the DMG

`__APP__.dmg` must already exist in the project root — building the archive is out of scope for this document.

Version and build are whatever the archive stamped. Read them from the DMG; do not guess. `scripts/release.sh` does this itself in step 4, or:

```bash
MOUNT=DebugArtifacts/release-dmg
mkdir -p "$MOUNT"
hdiutil attach __APP__.dmg -mountpoint "$MOUNT" -nobrowse -quiet
/usr/libexec/PlistBuddy -c 'Print :CFBundleShortVersionString' "$MOUNT/__APP__.app/Contents/Info.plist"
/usr/libexec/PlistBuddy -c 'Print :CFBundleVersion' "$MOUNT/__APP__.app/Contents/Info.plist"
hdiutil detach "$MOUNT" -quiet
rmdir "$MOUNT"
```

### 2. Write `../releases/__SLUG__/changelog.json`

Stop here for human confirmation. Draft the notes, show them, and do not write the file or continue until the user approves.

Use the version and build from the DMG. Prepend one object to `changelog.json`. Keep every older entry — the releases page lists them all. Do not commit; the script commits it with the feed.

Write notes from the user's point of view, from the commit range since the last published feed entry (the `Commit:` line on the previous GitHub release). Not commit-subject wording. If a message is ambiguous, read the diff.

Before drafting, **read the last three entries in `changelog.json`**. They are the style reference, not a suggestion — match their shape and voice; a draft that reads unlike them is wrong even if every fact in it is right. Beyond that:

- Say what the user can now do, or what stopped breaking. Never explain the mechanism or the OS behavior behind it.
- No chained purpose clauses, no explanatory tail. A semicolon joins parallel facts only, never a follow-up "and then…" / "which…" / "so that…" clause.
- Sentence case, no trailing period, no marketing adjectives. Shortcuts in parentheses.
- Bug items name the symptom, not the fix.

```json
{
  "version": "1.0",
  "build": 155,
  "notes": [
    {
      "title": "New Features",
      "items": ["…"]
    },
    {
      "title": "Bug Fixes",
      "items": ["…"]
    }
  ]
}
```

### 3. Tag the app

Tag the archived commit with the marketing version the DMG carries — no build number — then push the tag.

```bash
git tag "1.0"
git push origin "1.0"
```

### 4. Release

```bash
./scripts/release.sh
```

The script refuses to run if the newest `changelog.json` entry is not this DMG, if a release with this tag already exists, or if `../releases` is not level with `origin` with the new changelog entry as its only change. Then, in order:

1. Creates `__SLUG__-{marketing}-{build}` on `Stillmake/releases` with the DMG. Title is `{AppName} {marketing} ({build})`, and the body is the changelog entry as markdown with a `Commit:` line, which marks where the next release's notes start.
2. Regenerates `../releases/__SLUG__/version.json`, commits it with the changelog as `__SLUG__: {marketing} ({build})` and pushes. Each entry published in `Stillmake/releases` carries the `url` of its DMG, which the app downloads as-is. The app fetches `https://raw.githubusercontent.com/Stillmake/releases/main/__SLUG__/version.json` at most every two hours. Nobody is notified until this push lands, and it lands after the DMG is up.
3. With a homepage repo only: dispatches its Deploy workflow (`.github/workflows/deploy.yml`), which checks out Stillmake/releases, builds the site from it and deploys it to Cloudflare. Remind the user to confirm the run succeeds.
4. Runs `../homebrew-tap/scripts/bump.sh __SLUG__ __APP__.dmg`, which sets the cask's version and sha256 from the DMG and pushes the tap.

Publish for real — not a draft.
